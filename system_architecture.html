실시간 대기열 제어 흐름 (Waiting Queue Flow)

콘서트 예매 시 트래픽 폭주를 제어하기 위한 Redis ZSet 기반 대기열 처리 프로세스입니다.

1

대기열 진입 요청 (Next.js ➔ Spring Boot)

유저가 콘서트 상세페이지에서 예매 시도 시, API를 통해 대기열 등록을 요청합니다.

POST https://[Railway-Backend-URL]/api/concerts/{concertId}/schedules/{scheduleId}/waiting/register
2

Redis Sorted Set (ZSet) 대기열 등록 및 순번 계산

Lua Script를 실행하여 원자적(Atomic)으로 대기열 번호(Score)를 발급하고 랭킹을 확인합니다.

Redis Key: queue:wait:schedule:{scheduleId} (Sorted Set)
Score: Auto-Increment Sequence (INCR)
Value: userId
3

WebSocket STOMP 연결 & 실시간 순위 브로드캐스트

클라이언트는 `/ws`로 연결하여 본인의 대기 순위를 주기적으로 수신하고 화면에 표시합니다.

Subscribe: /queue/schedules/{scheduleId}/status (전체 대기열 상태 브로드캐스트)
Subscribe: /user/queue/schedules/{scheduleId}/entry (개별 유저 진입 허가 메시지 수신)
4

대기열 스케줄러 & Lua Script 진입 허가 (Admit Users)

스케줄러가 주기적으로 현재 예약 활성 사용자수(Active Set)를 체크하여 여유 슬롯만큼 대기열에서 유저를 활성화합니다.

Redis Active Key: queue:active:schedule:{scheduleId} (Score: 만료시간 타임스탬프)
진입 성공 시: UUID 기반 Active Entry Token 생성 (Redis 저장, TTL 10분)
5

예매 활성화 및 토큰 검증 후 좌석 선택 이동

진입이 허가된 클라이언트는 발급받은 UUID 토큰을 지참하여 좌석 선택 화면으로 진입하고, 예매를 시작합니다.

데이터베이스 관계도 (Entity Relationship Diagram)

콘서트 예매 핵심 도메인 모델과 JPA 엔티티 관계(ERD) 시각화 데이터입니다.

API Rate Limiting (디바이스별 트래픽 폭주 방어)

특정 매크로 기기나 봇이 좌석 상태 확인 API를 과도하게 호출하는 것을 방지하기 위해 구현된 처리 구조입니다.

Rate Limit 키 생성 기준

요청 사용자의 인증 상태에 따라 다이내믹하게 Bucket Key를 추출합니다:

  • 인증 회원: user:{userId}:schedule:{scheduleId}:seat-status
  • 비인증 회원: ip:{clientIp}:schedule:{scheduleId}:seat-status

토큰 버킷 설정 정책

Caffeine 로컬 캐시에 호스팅되는 Bucket4j 라이브러리 정책:

  • 최대 용량: 5개 토큰 (기본값)
  • 리필 속도: 1초당 5개 토큰 리필
  • 보관 기간: 10분 동안 미접속 시 캐시 자동 삭제

과호출 시 예외 흐름 (429 Too Many Requests)

API 요청 ➔ RateLimitInterceptor ➔ tryConsume(1) 실패 ➔ 429 HTTP 에러 (TOO_MANY_REQUESTS)
